**Status:** Phase 0 audit baseline
**Date:** 2026-05-08
**Scope:** Current implementation gaps against the stable latency execution semantics.

**Phase 1 note:** Central clock helpers and backward-compatible `clock` config resolution have been added. Executor scheduling, scheduler ordering, realtime behavior, hold policies, and logging schema remain as audited until later phases.

The stable execution contract remains in:

- `docs/latency_execution_semantics_en.md`
- `docs/latency_execution_semantics_zh.md`

This document is dynamic audit material. It records current-code behavior, suspected bugs, refactor targets, and tests needed. It must not redefine the stable semantics.

## Runtime Data Flow Summary

### Paused

`latency_bench/executors/paused.py` builds observations on scheduled decision steps, calls `policy.predict` synchronously, logs configured latency as metadata, sets effective latency to zero, enqueues the action as ready at the current time, updates the scheduler, and steps the environment. This matches the high-level paused idea that wall-clock inference does not advance environment time, but the exact observation/apply frame wording needs an explicit contract test before any change.

### Simulated

`latency_bench/executors/simulated.py` advances one wrapper env step per loop, emits observations through `DecisionScheduler`, samples latency in milliseconds, computes `ready_time_ms`, and lets `ActionScheduler` apply actions when ready. The important mismatch is that readiness is time-ms/wrapper-step based rather than canonical integer raw-frame based.

### Realtime

`latency_bench/executors/realtime.py` targets `EnvClock.frame_ms` wall-clock cadence and uses a single background `SerialPolicyWorker`. It can skip observations during catchup and uses a bounded drop-oldest pending queue. It does not yet model `max_in_flight`, default drop-new, timeout/skipped jobs, late-result ignore, or issue-order FIFO unblocking.
