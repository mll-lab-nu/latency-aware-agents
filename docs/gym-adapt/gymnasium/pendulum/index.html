02 · Reconnaissance

API facts versus task-author decisions

API FACT

  • Pendulum-v1, built into Gymnasium 0.29.1.
  • Action: Box(-2, 2, (1,), float32).
  • Observation: [cos θ, sin θ, angular velocity], shape (3,).
  • Physics timestep: dt=0.05 s, therefore 20 raw ticks/s.
  • RGB render: (500, 500, 3) uint8.
  • Native episode truncation after 200 steps; no normal task termination.
  • Native reward and dynamics retained, with g=10.0.

USER DECISION

  • Replace the continuous Box with five torques: [-2, -1, 0, 1, 2].
  • Freeze action order from hard clockwise to hard counterclockwise.
  • Use zero_torque as the delayed queue's pending action.
  • Treat one Gym step—not metadata render_fps=30—as one raw tick.
  • Observe every raw tick and evaluate fixed L1=50 ms.
  • Keep native observations, reward, time limit, reset distribution, and RGB renderer.

The synchronized API probe JSON is the source for runtime facts. The five-action catalog is deliberately labeled as user-approved rather than API-derived.

04 · Immutable task contract

One environment mapping across every stage

observation_stride = 20 / 20 = 1 · latency_raw_frames = ceil(50 × 20 / 1000) = 1

Complete frozen env block
env:
  name: gymnasium
  task_name: pendulum_discrete
  env_id: LatencyBench/PendulumDiscrete-v0
  registration_imports: [latency_bench.envs.gymnasium_pendulum]
  make_kwargs:
    base_env_id: Pendulum-v1
    render_mode: rgb_array
    torque_values: [-2.0, -1.0, 0.0, 1.0, 2.0]
    base_make_kwargs: {g: 10.0}
  env_fps: 20
  obs_fps: 20
  frame_stack: 1
  noop_action: zero_torque
  action_map:
    torque_clockwise_hard: 0
    torque_clockwise_soft: 1
    zero_torque: 2
    torque_counterclockwise_soft: 3
    torque_counterclockwise_hard: 4
  action_order:
    - torque_clockwise_hard
    - torque_clockwise_soft
    - zero_torque
    - torque_counterclockwise_soft
    - torque_counterclockwise_hard
  base_prompt: >-
    Swing the pendulum upright and keep it balanced by applying torque.
    Choose exactly one action from: torque_clockwise_hard,
    torque_clockwise_soft, zero_torque, torque_counterclockwise_soft,
    torque_counterclockwise_hard.

The four resolved configs were loaded with latency_bench.core.config.load_config() and their final env mappings compared equal. The exact emitted YAML is preserved in env_block.yaml.

05 · Contract propagation

Where the information is used

Gym factory

env.name=gymnasium selects the separate adapter; the registration import makes the task-owned ID available.

Action wrapper

The policy emits IDs 0–4. The wrapper maps them to the frozen torque array before native env.step().

Sample Factory

The integration stores task identity, ordered labels/values, no-op ID, prompt, clock, and constructor kwargs in config.json.

Latency-bench

The checkpoint ID is decoded through the same action order while the scheduler applies it one raw tick later.

10 · Isolation and limitations

What this adaptation changes—and what it leaves alone

  • The factory's existing env.name=gymnasium branch is reused; no new legacy dispatch is added.
  • Flappy Bird, Demon Attack, and Deadly Corridor builders, action mappings, preprocessing, clocks, and configs are untouched.
  • The original Gymnasium continuous action space is not preserved. This release task is the explicitly defined five-torque experiment.
  • The environment metadata advertises 30 render FPS, but physics advances at 20 Hz. The benchmark contract correctly uses the measured dt=0.05.
  • Only one seed, one catalog, one latency, and one training budget were run. Broader scientific claims require additional experiments.

For the normative adaptation procedure, see the Gymnasium adaptation guide. For the earlier continuous-action reference, see the Inverted Pendulum walkthrough.
